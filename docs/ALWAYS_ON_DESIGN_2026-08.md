# 常時予測アーキテクチャ設計書 — システム像・スペック要件・遅延見積り（2026-08-04）

`REDESIGN_PROPOSAL_2026-07.md`（部品選定の調査記録）の後続。方針転換:
**「詰まり検出を起点に予測する」のではなく「常に予測し続け、介入(音声再生)だけをゲートで制御する」**。
プロトタイプのゲートは手動ボタン。介入ポリシーは後から差し替え・調整可能な純粋関数とする。

---

## 1. この方向性で何ができあがるか

動作中のシステムは常に次の状態を維持する。

- ユーザーが話している間、**発話先端の約0.3〜0.6秒後ろ**を追いかける形で「次に言いそうな続き」候補
  （テキスト n本 + 確信度）が毎秒3〜5回更新され続ける
- 最良候補が変わるたびに本人声のPCMが先行合成され、常に「再生可能な音声」がキャッシュに待機
- ボタンを押した瞬間（＝ゲートが開いた瞬間）、**10〜30ms**でキャッシュ済み音声が鳴る
- 走行ログには (prefix, 予測, その後実際に言った内容) が自動で溜まり、
  一致率・鮮度・確信度の統計が人手アノテーションなしで得られる

### 状態機械はほぼ消える

handoff の IDLE→LISTENING→PREDICTING→CANDIDATE_READY→… は、常時予測では
「予測ループ（常に回る）」と「ゲート（開/閉 + cooldown）」の2つに縮退する。
介入条件の判定はすべてゲート側の policy 関数に隔離され、予測エンジンは判断を持たない。

```text
シグナル（予測側が常時出力）                ゲート（後で差し替える部分）
──────────────────────                ──────────────────────
候補テキスト n本                          policy(signals) -> play / stop
top-1 logprob・候補間一致度                 プロトタイプ: 「ボタン押下中か」
候補の鮮度（生成時刻・由来prefix）           将来: 無音時間×未完結度×確信度×VAP…
無音継続時間 / フィラー検出 / VAP継続確率      （YAML閾値 or 小さな関数、ホットリロード）
cooldown状態
```

## 2. アーキテクチャ（技術構成）

```text
[Mic 16kHz] → リングバッファ
   ├→ TEN VAD / MaAI(VAP)      … CPU、シグナル供給のみ（プロトタイプでは省略可）
   └→ Streaming ASR（差し替えIF。MVP: Azure Speech / ローカル化: Nemotron-3.5-ASR-Streaming）
        ↓ partial（150〜300ms間隔）
[予測ループ]  llama.cpp + Qwen3 Swallow 8B CPT（base、chatテンプレート不使用）
        KVキャッシュを発話先端に常駐させる:
          - stable境界にKVチェックポイントを保持
          - 毎サイクル: チェックポイント復元 → 不安定末尾(数〜十数トークン)を追記 → n本デコード
          - ASR巻き戻りは「毎サイクル末尾を貼り直す」設計により自動的に吸収
        ↓ 候補セット {text×n, logprob, 由来prefix, 時刻}
[TTS先行合成]  Qwen3-TTS Base 本人声クローン（旧 voice_clone_streaming_server.py 改良）
        最良候補が変わったときだけ再合成 → PCMキャッシュ（TTL付き）
        ↓
[ゲート] policy(signals) → [WASAPI排他 再生] / 即時停止
```

- **KV常駐が本方式の核**。毎サイクルのプリフィルは不安定末尾の数トークンだけなので、
  1サイクルの実質コストは「10トークン×n本のデコード」のみになる
- n=2〜3本のバッチデコードは重み読み出しが支配的なため、単発の約1.1〜1.3倍の時間で済む
- クラウドLLMではこの構造（相手側に発話先端のKVを保持し続ける）が組めない。
  ローカルLLM採用の本質的理由はTTFT数値ではなくこれ
- サンプリング初期値: temperature 0.3〜0.6 / top-p 0.9 / n=3 / max 10〜12トークン /
  句読点stop。確信度 = top-1平均logprob + 候補間の先頭一致

## 3. 遅延見積り

### 3.1 段階別内訳

「実測」= 出典のある実測値。「推定」= メモリ帯域等からの算出で **Phase 0 で要実測**。

| 段階 | 見積り | 根拠 |
|---|---|---|
| マイク→ASR入力（20msフレーム） | 20〜40ms | 仕様 |
| ASR partial確定 | 150〜300ms | Azure Speech の一般的観測値（非公式）。Nemotron はチャンク設定 80〜560ms+推論数十ms |
| KV復元+末尾追記 | 10〜30ms | 推定（数〜十数トークンのプリフィル+呼び出しオーバーヘッド） |
| デコード 10トークン×n=3 | **150〜250ms**（A6000, 8B Q8） | 推定: A6000帯域768GB/s → 8B Q8 ≈ 50〜65 tok/s × バッチ係数1.1〜1.3 |
| TTS初回チャンク（候補変化時のみ） | 150〜250ms | 実測系: 旧サーバ208ms(1.7B)、faster-qwen3-tts 152ms(0.6B/RTX4090) |
| TTS全体（10〜15文字 ≈ 音声0.8〜1.2s） | 200〜350ms | RTF≈5前後の実測から推定 |
| ゲート開→出音（キャッシュ命中） | **10〜30ms** | WASAPI排他・ストリーム事前オープン |
| 再生停止（バージイン） | <100ms | バッファクリアのみ |

### 3.2 エンドツーエンドの3指標

| 指標 | 意味 | 見積り |
|---|---|---|
| **予測鮮度ラグ** | 発話先端 → その内容を織り込んだ候補テキストができるまで | **約0.3〜0.6秒**（ASR + デコード） |
| **音声準備ラグ** | 発話先端 → 本人声PCMがキャッシュに揃うまで | **約0.5〜0.9秒** |
| **介入遅延** | ゲート開 → 音が出るまで | キャッシュ命中: **10〜30ms** / 不命中: 200〜400ms（その場合デコード済みテキストから合成 or 沈黙） |

- 更新レートは max(ASR partial間隔, デコード時間) で決まり、**毎秒約3〜5回**
- ボタン押下時にキャッシュが古い場合は、その瞬間の最新partialから再デコード（KV温存により
  ~200ms）→合成という救済パスを引ける（前回提案の「二段構え」はこの形で自然に残る）
- 将来ゲートを自動化した場合の総遅延 = 無音判定時間（350〜500ms、これは"詰まりの定義"であって
  実装遅延ではない）+ 確認猶予 + 出音 10〜30ms、という前回試算がそのまま成立する

### 3.3 遅延を悪化させる要因（設計上の注意）

- ASR partial間隔がループの実質クロック。Azureのpartialが遅い場合、LLMをいくら速くしても
  鮮度ラグは縮まない → ローカルASR化(Nemotron 160msチャンク等)が効くのはここ
- TTSとLLMを同一GPUに同居させる場合、デコードと合成が重なると相互に1.2〜1.5倍程度遅くなる
  （推定）→ 2GPU構成なら無関係
- Windowsの共有モード音声出力は+30〜60ms。排他モード(WASAPI exclusive)を使う

## 4. マシンスペック要件

結論: **現有環境（RTX A6000 48GB + RTX 4070 Super 12GB）は十分すぎる。単一のRTX 4090/5090
クラス1枚でも全ローカル構成が成立する。** 下限は12GB GPU 1枚（ASRをクラウドにする）。

### 4.1 構成パターン別

| 構成 | GPU | 配置 | ループ性能（推定） | 評価 |
|---|---|---|---|---|
| 最小 | 12GB ×1（4070 Super等） | LLM 8B **Q4**(~5GB) + TTS 0.6B(~2GB) + KV(~1GB)、ASRはクラウド | decode 50〜65 t/s → 候補更新 250〜350ms | プロトタイプ成立。品質はQ4/0.6Bぶん低下 |
| **十分（推奨基準）** | 24GB ×1（4090 / 5090） | LLM 8B **Q8**(~9GB) + TTS 0.6〜1.7B + ASR 0.6B まで全ローカル | 8B Q8 ≈ 70〜90 t/s → 更新 200〜300ms | 1枚で完結する基準ライン |
| **現有環境** | A6000 48GB + 4070S 12GB | A6000: LLM（8B Q8余裕、KV長大化も可）/ 4070S: TTS + ローカルASR | 更新 200〜300ms、GPU競合なし | 推奨。さらに32B比較・LoRA学習の余地 |
| 大型比較 | A6000 48GB | Qwen3 Swallow **32B** Q4(~19GB) | ~22〜30 t/s → 更新 400〜550ms | 精度検証用。常用は鮮度とのトレードオフ |
| DGX Spark級 | GB10 128GB | メモリ潤沢だが帯域273GB/s | 8B Q8 ≈ 18〜25 t/s → 更新 500ms超 | **本ループには不向き**。学習・バッチ評価・大型モデル実験向き |
| GPUなし | — | ASR/LLM/TTS全てクラウド | 鮮度ラグ 1.5〜2秒級 | ボタンデモは作れるが「速く正確な常時予測」の検証にならない |

### 4.2 GPU以外

- CPU: 8コア以上で十分（VAD/VAP/オーケストレーションは軽い。TEN VAD は RTF 0.015）
- RAM: 32GB（モデルロード時のバッファとログ処理）
- ストレージ: NVMe SSD（モデル計 10〜30GB + セッションログ。生音声を録る場合 ~115MB/h×16kHz）
- オーディオ: WASAPI排他モードが使えるインターフェース。ループバック排除のため
  ヘッドセットまたはエコーキャンセル前提
- VRAM内訳の目安: 8B Q8 重み8.5〜9GB / KVキャッシュ 8kコンテキストで約1.2GB(fp16、Q8化で半減) /
  TTS 0.6B 約2GB・1.7B 約4〜6GB / ASR 0.6B 約2〜4GB

### 4.3 スペックが効く場所・効かない場所

- **効く**: GPUメモリ帯域（デコード速度＝ほぼ帯域律速）。世代よりも帯域とVRAM容量を見る
- **効かない**: GPU演算性能の絶対値（10トークン生成では飽和しない）、CPU性能、
  介入遅延（キャッシュ再生なのでGPU性能と無関係に10〜30ms）

## 5. 実装順序（プロトタイプまで）

1. **ログ+リプレイ基盤**: 全イベントにmonotonicタイムスタンプ。録音セッションを同条件で
   再生し、以後の全比較（モデル・閾値・ASR差し替え）をここで回す
2. **予測ループ単体（音声なし）**: テキストを少しずつ流し込み、KV常駐方式の
   候補更新間隔・鮮度ラグ・一致率を実測 ← **本設計の数値検証はここで完了する**
3. ストリーミングASR接続（Azure Speech、IF差し替え可能に）
4. TTS先行合成キャッシュ + ボタンゲート → **プロトタイプ完成**
5. シグナル拡張（VAD無音時間・VAP・確信度）→ policy を宣言的設定で差し替え可能に

## 6. Phase 0〜2 で実測すべき未確定値

- A6000 / 4070S での llama.cpp 単発デコード速度（上表はすべて帯域からの推定）
- n=3バッチデコードの実係数
- Azure Speech の partial 間隔と巻き戻り頻度（日本語・実話者）
- Qwen3-TTS 0.6B vs 1.7B のTTFA・クローン品質（A6000/4070S実測）
- KV復元+末尾貼り直しの1サイクル実コスト（トークナイザ再分割含む）
- 予測一致率（先頭3モーラ一致など）のベースライン — 自動正解ラベルで測定
